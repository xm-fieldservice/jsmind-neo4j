# 审查员：工作报告细节审查清单

## 🎯 **核心使命**
系统性提醒审查员在审查工作报告时关注关键实现细节，避免"放水通过"问题计划

## ⚠️ **历史教训**
- 对明显重复实现计划"有条件通过"
- 不验证代码现状就批准计划
- 被程序员虚假数据误导 (47%-400%夸大)
- 没有逐项审核造成重大遗漏

## 📋 **系统性审查框架**

### **1. 数据真实性核查清单**

#### **文件存在性验证**
- [ ] 使用 `search_files` 工具验证所有引用的文件是否存在
- [ ] 使用 `list_files` 工具核对文件路径准确性
- [ ] 验证代码行号引用是否准确
- [ ] 检查文件大小和代码行数是否与报告一致

#### **功能重叠度验证**
- [ ] 使用 `grep` 搜索重复函数名和类名
- [ ] 分析代码相似度（复制粘贴检测）
- [ ] 验证功能重复百分比计算是否准确
- [ ] 检查是否遗漏了隐藏的重复文件

#### **性能数据验证**
- [ ] 验证性能指标是否基于实际测试
- [ ] 检查性能基准测试方法是否合理
- [ ] 验证性能改进百分比是否夸大
- [ ] 检查是否有性能回归风险

### **2. 关键实现细节审查清单**

#### **接口定义完整性**
- [ ] 所有新接口是否有完整的类型定义
- [ ] 接口方法签名是否明确（参数、返回值）
- [ ] 是否有错误处理机制定义
- [ ] 接口文档是否包含使用示例

#### **数据格式规范**
- [ ] 数据结构是否有明确的Schema定义
- [ ] 数据字段类型和约束是否明确
- [ ] 数据迁移方案是否详细
- [ ] 数据验证规则是否完整

#### **集成点定义**
- [ ] 与现有系统的集成点是否明确
- [ ] 集成接口的兼容性是否考虑
- [ ] 是否有回滚和降级方案
- [ ] 集成测试用例是否完整

### **3. 技术可行性审查清单**

#### **依赖关系分析**
- [ ] 新功能对现有系统的依赖是否明确
- [ ] 第三方库的版本兼容性是否验证
- [ ] 浏览器/环境兼容性是否考虑
- [ ] 性能影响是否量化分析

#### **实施复杂度评估**
- [ ] 代码重构的复杂度是否低估
- [ ] 数据迁移的复杂度是否考虑
- [ ] 集成测试的复杂度是否评估
- [ ] 部署上线的复杂度是否计划

#### **技术债务识别**
- [ ] 是否引入新的技术债务
- [ ] 现有技术债务是否得到解决
- [ ] 代码质量指标是否明确定义
- [ ] 维护成本是否合理评估

### **4. 架构合规性审查清单**

#### **设计原则遵守**
- [ ] 是否遵循DRY原则（无重复）
- [ ] 是否遵循单一职责原则
- [ ] 是否遵循开闭原则（扩展开放，修改关闭）
- [ ] 是否遵循依赖倒置原则

#### **框架使用规范**
- [ ] 是否基于现有框架扩展而非重写
- [ ] 是否违反框架的设计约束
- [ ] 是否合理使用框架提供的功能
- [ ] 是否避免框架反模式

#### **扩展性设计**
- [ ] 新功能是否支持未来扩展
- [ ] 接口设计是否足够抽象
- [ ] 配置是否外部化
- [ ] 插件化支持是否考虑

### **5. 风险评估审查清单**

#### **技术风险识别**
- [ ] 性能风险是否量化
- [ ] 安全风险是否评估
- [ ] 兼容性风险是否考虑
- [ ] 维护风险是否分析

#### **进度风险评估**
- [ ] 时间估算是否合理（参考历史数据）
- [ ] 关键路径依赖是否识别
- [ ] 资源需求是否明确
- [ ] 应急缓冲时间是否充足

#### **质量风险控制**
- [ ] 测试覆盖率目标是否合理
- [ ] 代码审查流程是否定义
- [ ] 质量门禁是否设置
- [ ] 监控和告警是否计划

## 🔍 **逐行代码审查方法**

### **代码引用验证**
```bash
# 必须执行的验证命令
grep -n "函数名" 文件路径    # 验证函数存在性
wc -l 文件路径              # 验证代码行数
find . -name "*.js" -exec grep -l "关键词" {} \;  # 验证文件存在性
```

### **功能重叠度计算**
```javascript
// 计算方法示例
function calculateOverlap(file1, file2) {
    const lines1 = readFileLines(file1);
    const lines2 = readFileLines(file2);
    const commonLines = findCommonLines(lines1, lines2);
    return (commonLines.length / Math.max(lines1.length, lines2.length)) * 100;
}
```

### **性能基准验证**
```javascript
// 性能验证要点
- 基准测试环境一致性
- 测试数据代表性
- 多次测试取平均值
- 对比现有系统性能
```

## 📊 **审查报告质量指标**

### **量化审查深度**
- **文件验证率**：验证的文件数 / 引用的文件数 × 100%
- **代码行验证率**：验证的代码行数 / 引用的代码行数 × 100%
- **功能重叠验证率**：验证的功能重叠计算 / 报告中的功能重叠声明 × 100%

### **审查完整性评分**
| 审查维度 | 权重 | 得分 | 说明 |
|---------|------|------|------|
| 数据真实性 | 30% |  | 文件存在性、代码准确性 |
| 技术细节 | 25% |  | 接口定义、数据格式、集成点 |
| 架构合规 | 20% |  | 设计原则、框架使用 |
| 风险评估 | 15% |  | 技术风险、进度风险 |
| 实施可行性 | 10% |  | 复杂度、资源需求 |

**总分 ≥ 80%**：可通过审查
**总分 60-79%**：有条件通过，需修改
**总分 < 60%**：拒绝通过

## ⚡ **审查员工作流程**

### **预审查准备**
1. **环境准备**：确保有完整的代码访问权限
2. **工具准备**：准备好搜索、分析工具
3. **标准准备**：明确架构合规性标准

### **审查执行**
1. **数据真实性核查**（30%时间）
2. **技术细节审查**（40%时间）
3. **架构合规性检查**（20%时间）
4. **风险评估**（10%时间）

### **审查报告**
1. **问题分类**：按严重程度分类问题
2. **具体证据**：提供代码位置和具体问题描述
3. **修改建议**：给出具体的修改建议
4. **验收标准**：明确通过审查的条件

## 🚨 **惩罚机制提醒**

### **审查员责任**
- 再次放水通过问题计划将被质疑专业能力
- 造成重大遗漏将承担相应责任
- 连续审查质量问题可能被免职

### **质量保证措施**
- 交叉审查：重要计划由多名审查员共同审查
- 审查记录：保留完整的审查过程和证据
- 持续改进：定期更新审查清单和方法

## 📝 **审查报告模板**

### **必须包含的章节**
1. **数据验证结果** - 逐项验证报告中的数据声称
2. **技术问题分析** - 详细分析关键实现细节问题
3. **架构合规性评估** - 基于架构标准的合规性检查
4. **风险评估报告** - 识别和量化各项风险
5. **具体修改建议** - 提供可操作的修改指导
6. **审查结论** - 明确的通过/拒绝决定

### **必须提供的证据**
- 代码位置引用（文件路径:行号）
- 搜索命令和结果
- 性能测试数据
- 架构图和技术文档引用
